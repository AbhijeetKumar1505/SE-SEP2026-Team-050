API Test Cases

This document lists the test cases for the platform's REST API (Milestone 3, SCRUM-77). The API is described in backend/openapi.yaml (58 operations), and every test case below is an automated pytest test in backend/tests/.

How this document was produced

  • Test cases. Each test case is one pytest test. Its name says what it checks. Tests that need more than one request, such as "sign up, then verify the link", list each request as a numbered step.
  • Inputs are the request body, query string or uploaded file the test sends. Long values are shortened with "…", and secret tokens are shown as {token}.
  • Expected output is what the test asserts: the HTTP status and the behaviour described by the test name.
  • Actual output was recorded by running the suite against the real Flask application with an in-memory SQLite database. It shows the status code and the start of the JSON body each request actually returned.
  • Result is Success when the test passed, which means every assertion on the actual output held.

Where the actual output differed from the expected, and the fix

Every test case passes today, but not every one passed the first time. The table lists each time a request's actual output differed from what was expected during Sprint 1, why, and how it was fixed. Each fix is now held in place by the test case named in the last column, so the problem would fail the suite if it came back.

# API Input Expected Actual (before the fix) Cause Fix Now checked by
D-1 PUT /api/students/me A profile update that also sends name and student_number The test expected 200 OK 422 Unprocessable Entity, "Unknown field." for name and student_number The API was right: name and roll number come from IIC's roster (US-02), so the schema refuses them. The test's expectation was wrong. The test now expects 422 and checks that the name and roll number are unchanged. PR #28 TC-031 (test_a_student_cannot_change_their_name_or_roll_number)
D-2 GET /api/mentors/me/dashboard A mentor who has an open capacity increase request 200 OK, with the request shown on the dashboard 500 Internal Server Error The dashboard showed who made the request with open_request.by_user.name, but a user account has no name (names are kept on the student or mentor profile), so it raised AttributeError. The dashboard uses display_name() for the requester. PR #32. It returns 200 with capacity_request filled in. TC-197 (test_iic_asks_a_mentor_and_the_mentor_is_told)
D-3 POST /api/mentors/{mentor_id}/verify {"expertise": ["Computer vision", "computer vision"]} 200 OK, the mentor verified with one "Computer vision" tag The request crashed on a duplicate tag The two spellings matched the same topic tag, so the tag was linked to the mentor twice. Tags are de-duplicated regardless of capitalisation before they are linked. PR #30 TC-116 (test_verifying_records_who_and_when_and_emails_a_7_day_activation_link)
D-4 POST /api/auth/verify-email The whole verification link pasted from the email, rather than only its token 200 OK, the account verified 404 Not Found: the link was reported as not valid The endpoint looked the full URL up as if it were the token. The endpoint accepts either the link or the token, and ignores surrounding spaces. PR #24 TC-016 (test_a_pasted_link_or_a_token_with_spaces_works)
D-5 POST /api/auth/signup Any sign-up in development mode The verification email is sent; nothing secret appears in the API log The full email, including the verification link, was printed to the API log Flask-Mail prints the whole SMTP exchange in debug mode. MAIL_DEBUG is off by default; set MAIL_DEBUG=true to see the exchange. PR #29 tests/test_app.py (a configuration test with no HTTP request)
D-6 POST /api/auth/verify-email The same verification link opened twice (React StrictMode runs the request twice under npm run dev) The second request says the account is already verified 404 "invalid link", which the page showed even though the first request had succeeded The first request used up the token, and the second could not tell a used link from an unknown one. Running the tests

From backend/, with the virtual environment active:

pip install -r requirements-dev.txt
pytest -v

CI runs the same command on every pull request, and stores the output as the pytest-output artifact of each run.

  • submitting a problem;
  • following it until a mentor accepted;

Overall: S01 found the flow intuitive and easy to follow without help, and their response was positive. They did not ask for any change to the Sprint 1 flow.

What S01 liked

  • Specific topic tags.   • A mentor page ready to act on. Once the mentor accepted, S01 saw the mentor's expertise, experience, preferred channel and contact details, and a first message already drafted for them. It was clear that the student makes the first contact, and how.

What S01 expects next. Most of S01's expectations are for what happens after the first contact, which Sprint 2 builds:

  • A mentorship that lasts beyond one conversation. In Milestone 1, every mentoring S01 had tried ended after a single conversation. S01 expects to:

  • activating the account from IIC's email;
  • setting availability and contact details;
  • reading an assigned student's request;

Overall: M01 found the flow intuitive and their response was positive. They did not ask for any change to the Sprint 1 flow.

What M01 liked

  • Context before committing. The assignment card shows the student's level, completed courses, career interest, problem, what they hope to achieve and the topic tags, with the hours left to respond. M01 could judge whether they could help before accepting. In Milestone 1, M01 said they mostly help people they already know. The card gives them the same context about a student they have never met.

  • Control over their own time. M01 liked these settings:

    • the Available for new students switch;
    • when they are free, and their time zone;
    • a capacity limit that IIC cannot go over without asking them first, and they can say no.

    In Milestone 1, M01 said they help in short, irregular slots, often late at night, so they want to decide how much they take on.

  • Declining without guilt. A decline needs only a reason from a short list, and the student goes straight back to the top of IIC's queue, so nobody is left waiting on them.

  • The student reaches out first, on the channel M01 chose, and sees M01's contact details only after M01 accepts.

  • Ending a mentorship cleanly. M01 wants to end a mentorship from their side, with a reason, when the goal is met or they can no longer continue (US-13).
